# 决策记录 · 超星答题助手

> 这份文件记录代码里每一个"可以换个答案"的地方，以及为什么选了现在这个。
> 修改任何 D-xx 对应的值之前，先看懂这里的代价说明。

## 一、需求边界

用户有两个诉求，合并成一个脚本：

1. **刷课**：视频、文档、章节跳转——原脚本（`unrival` v1.39）已经能用，不重做。
2. **答题**：章节测试原本靠"大学搜题酱"插件，有每日额度且要会员。改为**直接调用用户自己的大模型 API**。

关键判断：`GM_xmlhttpRequest` 不受浏览器 CORS 限制，所以纯油猴脚本可以直接请求大模型接口，不需要部署任何后端。这是整个方案成立的前提。

## 五、原脚本的两个问题（本次修正）

**问题 1：提交阈值算法有误**

```js
// 原脚本
Math.floor((totalQuestionNum - questionNum) / totalQuestionNum) * 100 >= accuracy
```

`Math.floor` 作用在比例上而非百分比上。10 题答对 9 题：`floor(0.9) * 100 = 0`，永远只有 100% 才成立。把 `accuracy` 改成 80 也还是按 100% 卡。

**问题 2：`accuracy` 的语义是错的**

它统计的是"成功填入答案的题数"，不是"答对的题数"——脚本无法知道模型答得对不对。所以本脚本改名为 `minAnswerRate`（作答覆盖率），并在日志里明确写"这是填写比例，不是正确率"，避免用户误以为交了满分卷。

**问题 3：选项匹配用双向 `includes` 会静默配错**

「人民」被「人民群众」包含、「马克思主义」被「马克思主义中国化」包含，字面上都满足 `includes`，但指向不同选项。本脚本改为带长度比下限的评分匹配（见 D-13）。

|----|--------|------|------|------|
| D-13 | 选项匹配策略 | 精确 100 分 / 长度比≥0.9 得 95 / ≥0.72 得 75 / 否则 0 | `50-matcher.js:37-54` | 0.72 这个下限是通过"人民 vs 人民群众"（0.5）和"1921 vs 1921年"（0.8）两个实测用例定的 |
| D-14 | 匹配接受阈值 | 55 分 | `50-matcher.js:10` | 低于字母兜底的 60 分，保证"文本没匹配上"时不会靠字母蒙 |

## 九、填入机制与风控面分析

### 9.1 填入是怎么做的

`70-runner.js` 的 `setOptionState(opt, wanted)`：

```js
// 1. 先读当前状态，已经是目标状态就直接返回（避免点两下把已选中的又取消掉）
const current = isOptionChecked(opt);
if (current === wanted) return true;

// 2. 滚动到可见区域（定制的 li 常要求元素在视口内才响应点击）
opt.clickEl.scrollIntoView({ block: 'center' });

// 3. 先点原生 input，最贴近真实交互
opt.input.click();
if (isOptionChecked(opt) === wanted) return true;

// 4. input 无效时点外层容器（超星把事件挂 li 上）
opt.clickEl.click();
```

状态判定分两种：原生 `<input>` 看 `.checked`；定制组件看类名里有没有 `cur` / `active` / `checked` / `selected`。

多选题的差别在于"要把不该选的点掉"——遍历全部选项，逐个比对目标状态。

### 9.2 和原脚本的对比

| 维度 | 原脚本（unrival） | 本脚本 |
|------|-------------------|--------|
| 点击对象 | 所有 `<li>` 里带 `em[id-param]` 的，直接 `li.click()` | 先 `input.click()`，失败再 `clickEl.click()` |
| 已选中保护 | 有，判断 `class` 是否含 `cur` | 有，`isOptionChecked` 统一判断 |
| 滚动到视口 | 无 | 有 |
| **填答案节奏** | **查一题填一题**，每题的查询被 `setTimeout` 错开到 2.5~4.5 秒 | **先并发查完再连续填**，每题间隔 300~800ms |
| 总耗时 | 较慢，随题量线性增长 | 明显更快 |

**关键差异在节奏**。原脚本的答案是一题一题回来的，点击天然分散在几分钟里；本脚本先并发把答案全取回来（3~8 秒），然后连续点击，整份作业的"作答动作"集中在一分多钟内完成。

### 9.3 风险到底在哪

先把风险面缩小一下：**大模型的请求是发给 `api.deepseek.com` 的，超星完全看不到**。超星能观测到的只有浏览器里的三件事——

1. 页面加载时间
2. 一串点击事件
3. 提交请求

所以风控信号集中在**时间特征**上，而不是"你用了 API"。具体说：

| 信号 | 是否可被检测 | 说明 |
|------|--------------|------|
| `event.isTrusted === false` | **技术上可检测** | 任何 `el.click()` 合成事件的 `isTrusted` 都是 false。但页面要主动监听并上报才有意义。超星是否这么做——**我无法确认**，没看到公开证据 |
| 作答总时长 | 极易检测 | 人类做 20 道选择题 6~12 分钟，脚本 1~2 分钟。这是**最明显的信号** |
| 点击间隔分布 | 可检测 | 完全等间距是机器特征；随机化能缓解 |
| 是否滚动、鼠标移动 | 可检测 | 脚本没有真实鼠标轨迹 |
| 多端同时在线 | 已检测 | 原脚本有 `detect.chaoxing.com` 的 iframe 埋点，`disableMonitor` 就是对付它的 |
| 视频进度签名 `enc` | 已检测 | 视频侧的主要风控，与答题无关 |

**结论**：`isTrusted` 这件事担心过头了——绝大多数网页脚本、自动化测试工具、浏览器插件产生的点击都是 `isTrusted: false`，如果超星据此封人，会误伤大量正常用户。真正容易出问题的是**作答时长过短**，这个信号干净、易算、误判率低。

### 9.4 已采用的加固（D-16 / D-17）

原先完全没有时长控制，20 题约 1 分钟完成。经确认采用最保守组合：

| ID | 决策项 | 候选 | 选定 | 理由 |
|----|--------|------|------|------|
| D-16 | 逐题点击间隔 | 300~800ms / 3~8 秒随机 | **3~8 秒随机** | 原脚本因为"查一题填一题"天然有这个间隔，我们并发取答案反而更快了，需要补回来 |
| D-17 | 总时长下限 | 不控制 / 按题数折算 | **题数 × 25 秒，不足则等待** | 20 题 = 8 分 20 秒，落在人类作答 6~12 分钟区间的中位 |

D-17 的 25 秒/题依据：大学生做一道四选一的选择题，读题 + 判断 + 点击大约 15~35 秒。取 25 秒是区间中位，既不显得敷衍也不至于让脚本干等太久。

计时起点取 `performance.timeOrigin`（页面加载时刻）而非点按钮时刻。原因是用户可能提前打开页面看了一会儿，那段时间超星一样算在内；用更早的起点意味着需要补的等待更少，也符合"超星看到的总时长"这个口径。

代价：一门课 10 个章节测试，每个约 8 分钟，全部跑完要一个多小时。这两项都可以在面板里关掉或调小。

## 十二、v0.1.1 变更（用户实测反馈）

用户在脚本猫里装完 v0.1.0 后的反馈：**"没有让我填 apiKey，也没有页面显示"**。

根因不是脚本没跑起来，而是设计错误：

1. 所有匹配页面无条件挂载面板，非答题页只是禁用「开始答题」并说明原因。
2. 未配置 key 时，齿轮上显示红点，并自动弹出设置面板（仅顶层 frame，避免多 iframe 各弹一个）。

4. 非答题页点「开始答题」时直接提示"先进入章节测试"，而不是让解析器空跑再报"没解析到题目"。
5. 增加了 `test/ui.test.js`（11 项），专门测"任意页面都能挂载 + 首次引导"。

**教训**：功能存在 ≠ 用户能发现。任何需要用户配置的工具，首次使用必须有可见的引导，不能依赖用户去找入口，更不能把提示只写进控制台。

### 版本号改为单一来源

同一轮反馈里用户还问"版本是 0.1.1 吗，为什么我看到 0.1"。原因是版本号写了两处：

- `header.txt` 的 `@version`（脚本管理器显示的是这个）
- `00-core.js` 的 `const VERSION`（控制台横幅和面板用的是这个）

改文档时两处都忘了动，于是自称 0.1.1、实际还是 0.1.0。

现在 `header.txt` 的 `@version` 是唯一来源，`build.js` 构建时把它注入到源码的 `__BUILD_VERSION__` 占位符，并在构建后校验产物版本与 header 一致，不一致直接构建失败。占位符缺失也报错，防止有人改回硬编码。

同时把版本号显示在面板标题和齿轮 tooltip 上，不用开 F12 就能确认装的是哪一版。

## 十三、v0.2.0 变更（中转站实测反馈）

用户在 river.ai 中转站上配置后反馈两点：**「测试连接」点了看不到成功还是失败**、**希望能像 ccswitch 那样列出可选模型**。

### 13.1 测试无反馈的根因（D-21）

`openSettings()` 里有 `this.panelEl.classList.remove('open')`——打开设置时把日志面板收起了。
而测试结果 `log(...)` 写在日志面板里，所以结果落在一个不可见的 DOM 里。用户看到的就是"点了没反应"。

### 13.2 请求格式（D-19）

用户贴出的 ccswitch 配置全是 `ANTHROPIC_*` 变量，说明那类网关走 Anthropic Messages 协议。
但查 river.ai 官方文档后确认：它**同时**提供 `POST /v1/chat/completions`（OpenAI 兼容）和 `GET /v1/models`，

即便如此仍加了协议选择，理由是：同类中转里确有只给 `/messages` 的，做成可选的成本很低，而返回 404 时用户无从判断原因。

两种格式的差异：

| | OpenAI | Anthropic |
|---|---|---|
| 路径 | `{base}/chat/completions` | `{base}/messages` |
| 鉴权 | `Authorization: Bearer` | `x-api-key` + `anthropic-version`（同时带 Bearer 兜底） |
| system | messages 里的一条 | 顶层字段 |
| max_tokens | 可选 | **必填** |
| 响应 | `choices[0].message.content` | `content[{type:'text'}].text` |

### 13.3 模型列表（D-20）

`GET {base}/models`。三种返回结构都兼容：`{data:[{id}]}`、`{models:[{name}]}`、纯字符串数组。

## 十四、v0.3.0 变更（iframe 误判 + 填空题）

用户在一张 60 题的章节测验上点「开始答题」，得到"当前页面不是答题页"。

### 14.1 误判的根因（D-22）

用户所在页面是：

```
mooc1.chaoxing.com/mycourse/studentstudy?chapterId=...&courseId=...&mooc2=1
```

这是**课程学习页**，不是作业页。章节测验渲染在页面内部的 iframe 里。
而 v0.2.0 的 `isQuizPage()` 只数顶层 `document` 的 radio/checkbox 数量——顶层是 0，于是判成"非答题页"。

修正：
- `Main.collectDocs()` 递归收集同源 iframe 的 document（最多 2 层，够覆盖超星结构）；
- `Main.resolveQuizDoc()` 按优先级定位：有 `.Py-mian1` → 有 ≥4 个 radio/checkbox → 有「填空」文本且存在 text 输入框；
- `Parser.parse(doc)` / `Runner.doc` / `findButtonByText(texts, doc)` 全部接受文档参数，不再写死顶层 `document`；
- `isVisible()` 改用元素所属文档的 `defaultView.getComputedStyle`——用外层 window 对另一个文档的元素取计算样式会拿到空对象。

**子框架不重复挂 UI**：顶层能访问时（同源），子框架的脚本实例直接退出，由顶层面板驱动子文档。否则一张卷子会冒出两个悬浮球。

**多次探测**：iframe 常常晚于脚本注入才渲染，探 6 次、每 2 秒一次；点「开始答题」时还会再强制重新定位一次。

### 14.2 填空题（D-23）

那份卷子 60 题 = 20 单选 + 20 多选 + 10 填空 + 10 判断。不做填空的话最多覆盖 50/60 = 83%，`minAnswerRate=100` 永远不满足。

实现：`AdapterBlank`，与选择题适配器**叠加**而非互斥（同一张卷子两种题型并存）。

- 识别：`input[type=text]` 且非搜索框，且所在容器文本含「第N空：」或「填空」；
- 分组：按 `.Py-mian1` 容器分组（一道题可能有多个空），退化到最近的含「第N空」的祖先；
- 题干：取 `.Py-m1-title`，剥掉「第N空：」标签；
- 提示词新增格式：`{"text":["答案1","答案2"],"confidence":0.9}`；
- 填入：走 `HTMLInputElement.prototype` 上的 `value` setter 再派发 `input`/`change` 事件——React 受控组件只认这条路，直接赋 `input.value` 它收不到。

### 14.3 不支持的题型必须拦住提交（D-24）

关键风险：覆盖率的分母是"脚本解析出来的题"。填空题**没解析出来**时它根本不在分母里，于是 50/50 = 100%，一路提交，交上去的是一张空着 10 道填空的卷子。

修正：`detectUnsupportedTypes()` 检测卷面是否有处理不了的题型；有则跳过自动提交，但仍然自动保存已填部分，并明确告知还差哪些题。

判定细节：
- 「填空题」只有在**页面确实存在 text 输入框**却一个都没解析出来时才报错，避免页面说明文字里提到题型就误伤；
- 「简答题/论述题/名词解释」一律视为不支持——脚本填不了富文本编辑器，这条宁可误报也不漏报。

### 14.4 新增测试

`test/iframe.test.js`（16 项）：复现"顶层无输入框"的原始场景 → 穿透 iframe 定位 → 解析三种题型 → 跑完整流程验证 DOM 真的被填上 → 验证含简答题时禁止提交。

### 15.1 三个叠加的错误

**错误一：只见类名，不见内容（D-25）**

v0.3.0 只有两个选择器：`.Py-mian1`（手机版）和"数 radio 数量"的启发式。
用户的页面是超星 web 端第三种结构——类名不认识，选项由自定义 `div` 组成，没有可用的 radio。

而页面上**明明写着 `【单选题】` `【多选题】` `【判断题】`**。这些是内容，不是类名，超星改版也改不掉。
所以新增 `AdapterByMarker`：找到所有含 `【题型】` 的最内层元素，向上爬到"装着这一题"的容器（判定标准是容器里至少有两个单字母标号，或至少一个文本框），再从容器里抽选项。

**错误二：按可见性过滤输入框（D-26）**

```js
.filter((i) => !i.disabled && isVisible(i))   // ← 旧代码
```

超星把 `input[type=radio]` 设成 `display:none`，选中样式放在外层 `li` 上。`isVisible` 一律返回 false，于是「通用解析」数到 0 个输入框，直接放弃。
去掉可见性过滤后，隐藏的 radio 依然能用来确定"哪几个选项属于同一题"，至于要不要点击，交给 `setOptionState` 的类名判断。

**错误三：简答题误报（连带 D-24 的判定收紧）**

旧逻辑是 `/简答题/.test(全页文本)`。页面上任何一处提到"简答题"（题型统计栏、说明文字）都会命中，然后永久禁止提交。
改为只认两种形式：`【简答题】` 题型标记，或 `简答题（共N题）` 小节标题。

### 15.2 适配器优先级

新增两个适配器后，顺序变为：

| 顺序 | 适配器 | 依据 | 特点 |
|------|--------|------|------|

| 2 | `cx-pc` | `.TiMu` / `.Zy_ulTop li` | 准，覆盖 PC 经典版 |

| 4 | `generic` | radio/checkbox 的 DOM 层级 | 最广，但对自定义组件无效 |

### 15.3 选项前缀剥离的新漏洞

- iframe 列表及其是否可访问
- 同时打到控制台并放进面板文本框，剪贴板失败也能手动复制


### 16.2 真正的原因：字体加密（D-31）

```html

```

`font-cxsecret` 是超星的字体加密。DOM 里的字被换成了别的字，靠自定义字体渲染回正确字形：

| 聚厩2035年建成文化强国战略廆标 | 聚焦2035年建成文化强国战略目标 |
| 我们厦深廅把握社会主廋文廇本质 | 我们要深刻把握社会主义文艺本质 |

所以模型读到的题干是「聚厩2035年建成文化强国战略廆标」，它当然答不出来，只能返回 0.30 / 0.00 的置信度。
这解释了为什么能读的题（第 12～18 题，题干没有生僻替换字）答得又准又快（0.95、0.98），读不了的题全是低置信度。

**解码的可行路径**（待实施）：字体已加载在页面里，可以用 canvas 渲染「被替换的字 + 自定义字体」得到正确字形，再与常用字表的正常字体渲染结果做位图比对，反查出原字。技术上行得通，但准确率取决于字体族差异，必须先在小样本上验证再上。

## 十七、v0.6.0 变更（不保存 + 字体解码）

v0.5.0 跑出了 60 题全解析、37 题作答、覆盖率 61.7%。用户手动点了停止，结果**一个字都没保存**。

### 17.1 停止时丢掉所有答案（D-32）

`finish()` 的结构是：

```js
if (this.stopFlag) { UI.setStatus('error','已中止，未提交'); return; }   // ← 在保存之前
...
if (rate >= cfg.minAnswerRate) { 提交 } else { 保存 }
```

用户点「停止」时 `stopFlag` 为真，函数直接返回，**保存分支根本没执行**。
另外保存按钮的实际文案是「暂时保存」，而 `SAVE_TEXTS` 里只有「保存」，精确匹配也找不到它。

修正：
- `SAVE_TEXTS` 补上「暂时保存」等实际文案；
- 抽出 `trySave(doc, cfg)`，让**所有结束路径**（正常结束 / 手动停止 / 有未支持题型 / 覆盖率不达标）都先尝试保存。

### 17.2 字体解码（D-31 / D-33）

v0.5.0 只检测不解码。这次实现了解码，方法见 `src/45-font.js`：

1. 用 `getComputedStyle` 问出加密字体族名（比解析 `@font-face` 可靠）；
2. 用 canvas 把 20902 个基本汉字用**页面正文字体**渲染成位图，压成 16×16 密度特征，建表；
3. 对每个可疑字，用**加密字体**渲染同一个字，得到正确字形，压成同样的特征；
4. 先和"它自己"比：像自己就说明没被替换，**原样放过**；
5. 只有明显不像自己时，才全表搜索最像的候选。

第 4 步是安全性的关键：普通文字一个字都不会被改，避免"本来对的字被改成近形字"这种更难发现的错误。

为什么不去解析 woff：浏览器已经把字形光栅化好了，借 canvas 直接比对，比自己读 cmap/glyf 表再光栅化省几百行代码，也少一堆出错点。

**风险与缓解**：解码准确率取决于加密字体和正文 body 字体的字形差异，我无法离线验证。
所以面板上加了「解码预览」按钮——先把「哪个字被还原成什么」打出来，用户确认读得通顺再答题。
解码开关在设置里可关。

`test/font.test.js`（12 项）：特征压平、距离计算、无 canvas 环境下的安全降级（表没建好时绝不改字）。

## 十八、v0.6.1 变更（点开始就卡死）

用户反馈：点「开始答题」或「解码预览」，页面直接卡住不动。

### 18.1 卡死的两个原因

**原因一：字形表同步构建（D-34）**

v0.6.0 的实现是一次性同步跑完：

```
for 20902 个汉字:
    ctx.fillText(...)          // 每批 3600 个
    getImageData(1920×1920)    // 每批读 15MB 像素
```

主线程被占满，浏览器的渲染、事件、滚动全部暂停。用户看到的就是「点了没反应，页面死掉」。

修正：
- 每批只渲染 2000 字，批与批之间 `await sleep(0)` 让出事件循环，界面始终可响应；
- 特征网格从 16×16 降到 12×12（匹配快 1.8 倍，辨识度仍够）；
- 建完表后**只缓存「加密字→真字」的小映射**（几十到几百条），不再保留几 MB 的位图表；
- 缓存键含字体族名 + `@font-face` 的 src 地址——超星轮换字体文件时地址变了，自动重建；
- 第二次打开页面直接命中缓存，跳过建表。

**原因二：题型标记定位遍历了所有元素（D-35）**

```js
doc.querySelectorAll('div,li,dd,section,article,p,span,...')   // 上万个元素
  对每个读一次 el.textContent                                  // 每次遍历整棵子树
```

60 题的作业页 HTML 里元素数以万计，这个 O(元素数 × 子树大小) 的扫描非常慢。
改成 `TreeWalker` 只扫文本节点——文本节点的父元素本身就是要找的"最内层元素"，
既快一到两个数量级，还省掉了"子元素是否也包含标记"的判断。

| 场景 | 耗时 | 界面 |
|------|------|------|
| 首次解码 | 约 5~15 秒，有进度提示 | 可正常滚动、可点停止 |
| 之后同一字体 | 瞬间（读缓存） | — |

## 十九、参考：原脚本（unrival v1.39）的答题是怎么做的

项目起点是作者原来用的刷课脚本，它的答题模块逻辑值得记一笔，避免以后走回头路。

### 19.1 三段式，且不解析题目语义

**① 定位题目**——只有一个选择器：

```js
questionsElement = _d.getElementsByClassName('Py-mian1');
question = questionElement.getElementsByClassName('Py-m1-title fs16')[0].innerHTML;
question = question.replace(/(<([^>]+)>)/ig, '')...;     // 正则去标签
let optionTextE = trim(optionE.innerHTML);
let optionText = optionTextE.slice(1);                    // 砍掉首字符当字母
```

没有适配器、不跨 iframe、不解字体。选项文本靠 `slice(1)` 去字母，所以「AI技术」会被切成「I技术」——和 v0.4 修过的是同一类问题。

**② 取答案**——查第三方题库，不推理：

```js
url: 'https://cx.icodef.com/wyn-nb?v=4',
headers: { 'Authorization': token },
data: 'question=' + encodeURIComponent(question) + '&type=0&id=' + wid
// 失败再降级到 host + 'chaoXing/v3/getAnswer.php'
```

题库存了才有答案，没存就返回"未找到"。这就是用户当初反馈"题库很少、很多答不上来"的根因。

**③ 填入**——按 `id-param` / `val-param` 找 `li` 后 `li.click()`。

### 19.2 为什么它在当前页面 0 题

两道门同时关闭：

1. **URL 门**：答题分支挂在 `_l.href.indexOf("work/phone/doHomeWork") > 0`。当前页面是 `mooc-ans/work/doHomeWorkNew`，这个 `else if` 根本不会进入。
2. **结构门**：即使用户手动改 URL 绕过第一道门，`.Py-mian1` 数量为 0（实测导出确认），`questionNum = 0`，循环一次都不跑。

所以不是"它解析得更好"，而是"它只需要在结构固定、字体不加密的手机版页面上工作"。

### 19.3 结论：不采用它的方案

| 维度 | 原脚本 | 本项目 |
|------|--------|--------|
| 页面 | 仅 `work/phone/doHomeWork` | 多适配器 + 内容兜底 |
| 结构 | 仅 `.Py-mian1` | 类名 / `.TiMu` / `【题型】` |
| iframe | 不支持 | 穿透同源框架 |
| 字体加密 | 不需要 | canvas 位图解码 |
| 答案 | 第三方题库（需 token） | 用户自己的模型 |
| 填空题 | 不支持 | input + UEditor |
| 匹配 | 双向 `includes` | 带长度比的评分匹配 |

唯一值得借鉴的是"查表比推理准"，但代价是依赖他人维护题库与 token。走向量问答就必须自己解决"读不懂字"，也就是第十八节之前的字体解码工作。

### 19.4 它的题目从哪里查

**主接口**——第三方题库服务商 `icodef`：

```js
ctUrl = 'https://cx.icodef.com/wyn-nb?v=4'
method: 'POST'
headers: { 'Authorization': token }        // 脚本里硬编码 n4LoeX7VdngGIKS6
data: 'question=' + encodeURIComponent(题干) + '&type=0|1|3&id=' + wid
```

返回 `{ code, data }`。`code === -1` 表示题库里没有这道题。

**备用接口**——作者自建服务器：

```js
url: host + 'chaoXing/v3/getAnswer.php?tm=' + 题干 + '&type=' + type + '&wid=' + wid + '&courseid=' + courseId
```

`host` 即 `http://211.99.98.10:55234/`。

### 19.5 这台服务器还做了什么

同一台 `211.99.98.10:55234` 在原脚本里承担四件事：

| 路径 | 用途 | 是否涉及用户数据 |
|------|------|------------------|
| `chaoXing/v3/getEnc.php` | 视频进度签名 | 是（班级/用户/任务 id、观看时长） |
| `chaoXing/v3/getAnswer.php` | 题库查询 | 是（完整题干） |
| `chaoXing/v3/ads.php` | 广告下发，注入面板 | 否（只收不发的展示内容） |
| `api/hookHTML` | **上传整页 HTML** | 是（整页 outerHTML） |

`hookHTML` 挂在 `window.onload` 上，页面加载即把 `document.documentElement.outerHTML` 编码后 POST 上去：

```js
enc: btoa(encodeURIComponent(document.getElementsByTagName('html')[0].outerHTML))
```

名义上是众包题库。

**对本项目的约束**：D-11 确认保留该服务器用于视频 enc，但**只用于 enc**。本项目不实现 `hookHTML` 上报、不实现 `ads.php` 广告拉取——原脚本那两项与功能无关，只增加隐私暴露面。

### 19.6 「题库很少」是结构性问题

原方案不推理，只查表；表靠众包积累。冷门课程、新出的专题（例如用户这份「新大众文艺」）大概率没有收录。

两代方案的本质差别：

- 原脚本：**问别人"这道题答案是什么"** —— 查到就是标准答案，准；但覆盖面受题库限制。
- 本项目：**把题目读给模型让它自己想** —— 覆盖面广，但前提是题目文本可读，因此必须解决字体加密。

## 二十、v0.7.0 变更（题库优先 + 模型兜底）

用户提出：既然原脚本查题库基本都对，能不能**能查到题库的走题库，查不到再走模型**。

### 20.1 一个关键观察（D-37）

如果题库是靠 `hookHTML` 上传页面 HTML 众包积累的（见 19.5），那它存的题面可能是**加密态原文**——「聚厩2035年建成文化强国战略廆标」。

这意味着：**用解码后的正常文字去查反而查不到，必须用原始乱码查。**

两种可能都存在（早期手机版页面没有加密，存的是正常文字；新版页面众包上去的是乱码），所以查询时两种形式都试：

```
先查解码后的文本 → 未命中再查加密态原文
```

为此 `Parser.parse` 在解码前把原文留在 `q.rawStem` 里，否则解码后原文就丢了。

### 20.2 两级策略（D-36）

```
缓存命中 → 用缓存
  ↓ 未命中
题库查询 → 命中且能匹配选项 → 用题库答案
  ↓ 未命中或匹配失败
模型调用 → 正常流程
```

日志会标明每道题的答案来源：`（题库）` / `（缓存）` / `（模型 0.95）`。可信度不同，用户看得见。

### 20.3 采信条件（D-38）

题库返回的答案**必须能匹配上页面上的真实选项**才算数。

原因：题库里可能存着同一道题的另一版（选项顺序不同、选项措辞改过）。这时答案文本对不上，硬填等于瞎选。
匹配不上就丢弃，继续走模型，并在日志里说明。

### 20.4 失败处理

题库接口连续失败 2 次就整轮停用（`QuestionBank.disabled`）。

## 二十一、v0.7.1 变更（多选题只选一个）

### 21.1 bug：题型判定只看 checkbox（D-39）

`detectType()` 的判据是"选项里有没有 `input[type=checkbox]`"。但超星把选项做成带 `role="radio"` 的 `li`，底下**没有原生 checkbox**——多选题也一样。

结果：多选题被判成 `single`，`matchAnswer` 走单选分支，模型给的多个答案被忽略，只点一个选项。

修正：题型判定改用页面自带的信息，优先级从高到低：

1. 题干里的 `【多选题】` / `【判断题】` / `【单选题】` 标记（内容信号，最稳）
2. 选项 `li` 上的 `qtype` 属性——超星约定 `0` 单选、`1` 多选、`3` 判断
3. 手机版的 `input[id^="answertype"]` 的 value
4. 兜底才看输入框类型

`questionTypeFromDom()` 统一了这四级判断，手机版、PC 版、标记版三个适配器都改用它。

### 21.2 「复制出来没乱码」是一种错觉

用户看到新卷子复制出来的文字读着通顺，以为没加密。实际上替换字更"像"正常字了：

| 复制得到 | 实际内容 |
|---|---|
| 全**怰**治理走**怬怮**的十**怭**路口 | 全**球**治理走**到新**的十**字**路口 |
| **怮**威胁**怮**挑战**怲**增无减 | **新**威胁**新**挑战**有**增无减 |
| 世界进**愜怮**的动荡变革期 | 世界进**入新**的动荡变革期 |

怰→球、怬→到、怮→新、怭→字、怲→有、愜→入。

这些替换字集中在 U+602C–U+6032 一带的连续码位，且同一个假字始终映射到同一个真字——正是字体替换的典型特征。

**教训**：判断"有没有加密"不能靠人眼能不能读懂，要看 DOM 里有没有 `.font-cxsecret`，或者直接对比几个高频字的编码。人能靠上下文脑补，机器不能。

### 21.3 题库为什么没生效

`bank.enabled` 默认 `false`，`endpoint` 和 `token` 默认都是空——脚本不预置任何人的凭据。
不填就不可能命中，日志里会是「题库命中 0 题」。设置面板第 5 节需要手动开。

> **已在 v0.7.2 修正**：改为默认启用并内置原脚本那套接口与 token，见第二十二节。

另外这份卷子是 2025 年「全球治理」专题，属于很新的内容，公共众包题库大概率没有收录。

## 二十三、v0.7.3 变更（解码把对的字改错了 + 多选仍只填一个）

### 23.1 解码问题：参照字体取错了

用户日志里出现了一对矛盾：`字体解码已应用：60 道题的题干被还原` 和 `模型读到的是乱码` 同时打出来。
看实际还原结果才明白——**解码结果是另一种乱码，比不解码还糟**：

| 正确 | DOM 原文（加密） | 解码结果（错） |
|---|---|---|
| 阴**霾** | 阴霾（本来就是明文） | 阴**麤** |
| **新**威胁 | **怮**威胁 | **斸**威胁 |
| **有**增无减 | **怲**增无减 | **蓇**增无减 |
| **进**入 | **迸**入 | **迸**入（没解出来） |
| **动**荡 | **劭**荡 | **劭**荡（没解出来） |
| 变**革** | 变**華** | 变**華**（没解出来） |

注意第一行：**「霾」本来是明文，却被改成了「麤」**。这说明整张参照表都不对，不只是加密字解不准。

根因在 `detectRefFont`：

```js
const first = getComputedStyle(body).fontFamily.split(',')[0];  // → "Microsoft YaHei"
```

超星 PC 页的 body 是微软雅黑，而加密字体是**宋体子集**。两套字形差异很大（无衬线 vs 衬线、笔画粗细），于是每个字的特征都对不上 → 连明文的 `selfDist` 也超阈值 → 全表搜索 → 落到近形字上。

修复三处：
1. 参照字体固定为 `REF_FONT`（SimSun / 宋体 / STSong 链），不再从页面继承；
2. 解码时的 `ctx.font` 把 `REF_FONT` 作为 fallback 串在加密字体后面，加密字体未覆盖的码位回退到宋体，和参照表同源，`selfDist≈0` 自然不改；
3. 缓存键改成 `v2|refFont|family|url|grid`——不带版本会一直命中那份错的 211 字映射。

### 23.2 新增自检：解不准就一个都不解

D-31 原来的取向是「检测并告知」，这版升级为「检测、自检、不可信就停用」：

- 从 `.font-cxsecret` **之外**采集汉字当对照组（这些字是明文，理论上一个都不该被改）；
- 逐字解码，统计被改写的比例；
- **>5% 就整轮放弃**，清空映射、`giveUp=true`（本次会话不再重试，否则每次点开始都要白等十几秒），日志写明改错了哪几个字。

判据是「误伤率」而不是「还原率」：还原率高只说明改了字，误伤率低才说明改对了。

### 23.3 多选题还是只填一个：缓存污染

`matchMulti` 本身没问题，问题在它压根没被调用——**缓存直接命中了**。

v0.7.1 之前把多选题误判成单选，只点第一个选项，而这些**错误答案被原样存进了缓存**。修好判定逻辑后缓存照旧返回单字母，`[].concat('B')` 只有一个元素，于是还是只填一个。改代码看不出问题，因为没走到匹配逻辑。

修复两层：

| 措施 | 实现 |
|---|---|
| 规则变更时整库作废 | 缓存键带版本 `llmq:cache:v3`，旧键数据自然读不到（D-44） |
| 读取时校验类型 | 多选题答案必须是数组、判断题必须是 `'true'`/`'false'`，否则视为未命中重新问（D-44） |

第二层是防御性的：以后即使再出现类似规则变更，脏数据也不会被静默采信。

### 23.4 提示词：区分「字不认识」和「题不会做」

原来的规则是「信息不足就把 confidence 设为 0」，模型看到乱码就一律返回 0.3，导致大面积跳过。
用户的原话是「大模型明明可以回答」——确实，人能靠上下文脑补，模型也能，只是提示词没让它这么做。

新增指引：题干里出现笔画相近的生僻字属于**字体反爬的排版问题，不是题目本身有问题**，请按上下文还原成通顺词句后再作答，能还原就给 0.6 以上；只有整句都无法理解时才设 0。

同时也改掉了 Runner 里那条矛盾的日志：解码成功就报「已解码 N 道题」，解码没生效才报「模型读到乱码」。

## 二十四、v0.8.0 变更（字体加密真正被逆向出来了）

### 24.1 结论先说：位图法是死路，换成了字形轮廓哈希

v0.7.x 一直在调 canvas 位图比对：换参照字体、加自检、调网格精度。方向就是错的——

- 位图只能比对**外观**，12×12 网格下「己/已/巳」这类宋体近形字本来就分不开；
- 参照字体必须和加密字体**同源**才能比，一旦不同源，每个字都会落到近形字上；
- 最要命的：**它永远不会报错**，只会给出一个「看起来正常」的错字。

正确的做法是看字体的**结构数据**，而不是渲染结果。

### 24.2 逆向出来的机制

查公开的超星字体逆向资料，机制是明确的：

**超星把思源黑体的「码位 → 字形」映射重排了一遍。**把 U+602E 指向「新」的字形，浏览器渲染出来是正常的「新」，而 DOM 里存的还是「怮」。

关键点：**字形本身没改，只是换了挂载的码位。**

字体内嵌在页面里：

```html
<style id="cxSecretStyle">
@font-face { font-family: font-cxsecret; src: url("data:application/font-ttf;base64,...") }
</style>
```

解法四步：

1. 从 `style#cxSecretStyle` 取 base64 TTF；
2. 用 Typr 解析，对每个字符取 `Typr.U.glyphToPath` 的字形轮廓路径；
3. `JSON.stringify(path)` 后做 MD5，取末尾 8 位十六进制；
4. 查预置的「哈希 → 汉字」表。

因为哈希只取决于字形、与码位分配无关，所以**一张表通吃所有页面**。每页字体文件都不同（大小、SHA-256 全变），但同一个汉字的哈希永远一样——公开资料的实测是 8 份不同章节测验，未知字符 0。

### 24.3 三个关键设计

| 设计 | 原因 |
|---|---|
| 只解页面上出现过的字符 | 没必要遍历整个 cmap；超星字体也只收录这一页用到的字 |
| 命中率 <60% 或全不命中就停用（D-46） | 表与字体不匹配时硬解会产出「看起来正常的错字」，比不解危险 |
| `giveUp` 标记本次会话不再重试 | 否则每次点「开始答题」都要重新解析一遍才再次失败，用户以为卡死 |

`available()` 也改了：**不能只看有没有 `.font-cxsecret` 这个 class**。医学英语那类页面挂了 class 但没有对应的 `@font-face`，文字本来就是明文——只看 class 会误报，然后白解一次。

### 24.4 体积代价

| 组成 | 体积 |
|---|---|
| 对照表（20902 条，压成「哈希串 + 汉字串」两个平行字符串） | 226 KB |
| Typr 字体解析库（内联，MIT） | 97 KB |
| 其余源码 | 167 KB |
| 合计 | 约 490 KB |

表的压缩方式：对象字面量 `{"hash":码点}` 的引号和冒号本身占了三分之一体积；改成两个平行字符串（哈希串每条定长 8 字符 + 汉字串一条一个字符），运行时切一次建 Map，省掉约 130KB。

表里有 4 条键长不是 8 的脏数据（生成脚本的边角 bug），`gen-table.js` 会筛掉——不筛会按固定步长切片时整串错位，一条坏数据毁掉全表。

### 24.5 表的来源与风险（如实记录）

- 来源：公开的超星字体逆向研究项目（`tools/cx-glyph-table.json` 为其导出），**不是超星官方的东西**；
- 它属于社区成果，无正式许可说明；本项目只使用其中的**映射数据**，没有包含对方的代码；
- **可能过期**：超星若换基础字体（不再用思源黑体）或调整轮廓，哈希全变，表即失效；
- 失效时的表现是可控的——命中率检查会拦住，日志写明失败原因，退回原始文本，不会静默产出错字。

### 24.6 新增/重写测试

`test/font.test.js` 全部重写（38 项）：

- **自实现 MD5 与 Node crypto 逐字节一致**，含 55/56/64 字节的分块边界（错一位全表失效）；
- base64 解码字节级一致；
- 表结构自检：哈希串长度必须 = 条目数 × 8，随机抽 200 条验证切片没错位；
- 字体定位：标准内嵌 base64、外链 woff、**只有 class 没有 @font-face 时不能误判**、无字体时的兜底；
- **真实字体链路**：读系统黑体造一个假页面，断言「字形与表不符时必须返回 false、置 giveUp、一个字都不改」。

`test/realpage.test.js` 相应调整 1 项：那段 HTML 只有 class 没有字体，断言改为**不误报为加密**。

总计 309 项。

### 25.2 「填完了却不保存」——两个分支漏了

用户反馈：答案全填对了，但页面上「暂时保存」一次都没被点。

`finish()` 有 5 条结束路径，之前只有 3 条会尝试保存，漏了两条：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 覆盖率达标 + 自动提交**关闭** | 只打日志就 return | **保存** |
| 自动提交开启但**找不到提交按钮** | 报错 return | **先保存再报错** |

原则很简单：**只要填过答案，任何离开路径都得先尝试保存**。填完就撒手不管，用户一刷新全丢。

### 25.3 顺手修了按钮定位

`findButtonByText` 原来是**精确匹配**，超星的按钮文案一旦带后缀（如「暂时保存（Ctrl+S）」）就找不到。改成精确优先、失败后用**前缀**兜底匹配，长度上限从 12 放宽到 16。

限定「开头」而不是「包含」是必须的：找「提交」时用 includes 会把「暂时保存」也捞进来。

## 二十六、v0.8.4 变更（提交被拒 + 答案消失）

### 26.1 现象

60 题全填满、日志显示「已点击提交」，但：

- 页面弹出「还有题未完成，确定要提交吗」
- 点了确定之后，**填好的答案全部消失**
- 提交没有成功

### 26.2 三个原因

**① 提交前一票确认，不看对方说什么**

```js
pageWin.confirm = function () { return true; };   // 原来的实现
```

不管弹的是「确定保存吗」还是「还有 10 题未完成，确定提交吗」，一律点「是」。
超星拒收后页面重置，答案自然没了。这是**答案消失的直接原因**。

**② 覆盖率是脚本自己算的，超星看的是它自己的字段**

`rate` 统计的是「脚本认为填成功的题数」。超星判定完成看的是每题的 `input[name="answerXXX"]` 值、填空题的 `#inpDiv` 内容。两者不一致时，脚本以为 100%，超星认为缺 10 题。

**③ 填空题的 UEditor 可能没同步到超星的回传容器**

`UE.getEditor(id).setContent(v)` 理论上会触发 `contentChange` 去更新 `#inpDiv`，但实测有版本绑不上——编辑器里看着有字，超星读的容器还是空。10 道填空全中，正好对上「还有 10 题未完成」。

### 26.3 修复

| 措施 | 具体做法 |
|---|---|
| 提交前自检 | `auditAnswerState()` 逐题读页面真实状态（input value / inpDiv 内容 / 选中样式），发现漏题就**不提交，改为保存**，日志列出题号区间 |
| 拦下危险确认框 | `clickWithConfirm` 加 guard：confirm 文本命中 `未完成\|还有N题\|未作答` 就返回 false，绝不自动确认；DOM 弹层同样识别并点「取消」（D-47） |
| 检测失效时放行 | 如果**全部题**都判成未填，说明是超星改了字段名、核对方法失效，此时跳过自检直接提交，否则会永远卡住 |
| 填空补写 | `setContent` 之后再显式补写一次 `#inpDiv`（幂等），覆盖 contentChange 没绑上的版本 |

### 26.4 关于「强行提交」

即使超星说未完成，用户点了确定，结果也是被服务端拒回 + 页面重置。所以**拦下来保存**是唯一正确的选择——宁可让用户手动补那几道题，也不能把 50 道已答的答案一起丢掉。

## 二十七、v0.9.0 变更（保存/提交为什么点了没反应）

### 27.1 根因：改错了 window

```js
const pageWin = (typeof unsafeWindow !== 'undefined') ? unsafeWindow : window;
```

`unsafeWindow` 是**顶层** window。而超星的作业页在 `iframe#frame_content` 里，`confirm` 是 iframe 自己的一份，页面函数（`noSubmit` / `submitCheckTimes`）也挂在 iframe 的 window 上。

所以 v0.8.4 那套「拦截未完成确认框」**从装上的那一刻起就没生效过**——弹框来自 iframe，我们改的是顶层。用户看到的仍然是原生 confirm 阻塞，脚本靠 `findButtonByText(['确定'])` 去点，行为完全不受控制。

**这类 bug 的特点**：代码逻辑正确、测试也过（jsdom 里只有一个 window），但在真实的分帧页面上等于没写。

### 27.2 改法：跟原脚本学

原脚本（unrival）的作业部分根本不点按钮：

```js
if (正确率达标 && unrivalAutoSubmit) {
    submitCheckTimes();          // 页面自带的提交
} else if (unrivalAutoSave) {
    _w.noSubmit();               // 页面自带的保存
}
```

直接调页面函数，绕开按钮文案和确认框。现在也走这条路：

| 优先级 | 保存 | 提交 |
|---|---|---|
| 1 | `noSubmit` / `saveAnswer` / `saveWork` / `tijiaoSave` | `submitCheckTimes` / `submitWork` / `tijiao` |
| 2 | 点「暂时保存」类按钮 | 点「提交」类按钮 |

`winOf(doc)` 取的是**实际答题文档**的 window（`doc.defaultView`），`callWithGuard(win, guard, fn)` 在调函数期间临时装 confirm 守卫，因为页面函数内部也可能自己弹确认框。

### 27.3 三档设置

用户明确要求"能自己提交"：

| 选项 | autoSave | autoSubmit | 行为 |
|---|---|---|---|
| 只填好，我自己保存 / 提交 | false | false | 一个按钮都不点 |
| 自动保存，我自己提交（默认） | true | false | 调保存，不提交 |
| 自动保存并提交 | true | true | 保存 + 提交 |

配置层仍是两个布尔（`autoSave` / `autoSubmit`），UI 上合成一个三选一下拉，旧配置不用迁移。

manual 档也会跑一次自检，把可能被判"未完成"的题**提前告诉用户**，免得他手动点提交时又被打回来。

### 27.4 新增诊断导出

## 二十八、v0.9.1 变更（识别到答案却没填进去 + 等待太久）

### 28.1 answertype 陷阱：自检从装上起就是假的

```js
box.querySelector('input[name^="answer"]')
```

`answertypeXXXX` 也以 `answer` 开头，**`querySelector` 返回的是文档里靠前的那个**——通常正是 `answertype`。它存的是题型（0/1/3），永远非空。

所以 `auditAnswerState` 的结论永远是"没有未完成的题"，v0.8.4 加的提交前自检**形同虚设**。

修复：`readAnswerValue()` 遍历所有匹配项，跳过 `/^answertype/i`，取第一个真正的答案字段。

**教训**：属性前缀匹配是常见陷阱，`name^="answer"` 这种写法必须确认没有 `answerXXX` 的兄弟字段。

### 28.2 已选中的选项被点掉

用户看到的「识别出答案但没填」＋「可能是之前我就选好了，你给他按掉了」这个猜测是对的。

`isOptionChecked` 原来只认两种信号：原生 `input.checked`、类名里的 `cur/active/checked/selected/on`。超星 PC 版的选项是 `<li>`，没有原生 input；如果它的选中类名不在这个白名单里，判断就恒为"未选中"。

于是对着**已经选好的选项再点一下**——定制组件的点击是 toggle，答案就被点没了。

修复两层：

| 措施 | 做法 |
|---|---|
| 状态判断加一条权威通道 | `isOptionChecked(opt, box)` 在类名判断不出来时，读 `readAnswerValue(box)` 看 value 是否包含该选项字母 |
| 点完再核一遍（D-50） | `verifyChoiceValue(q, wanted)` 按超星字段核对；不一致就**自动重试一次**，仍不一致才算失败 |

多选题的核对用集合相等（既不许少选，也不许多选），单选/判断用包含判断。

### 28.3 等待太久：加「跳过等待」

60 题 × 25 秒 = 25 分钟。用户填完只想赶紧交，干等 19 分钟显然不合理。

面板上新增 **跳过等待** 按钮：只在等待阶段有效，跳过剩余时长直接进入提交/保存环节，**不改变"要不要提交"**（那是设置里的三档决定的）。

设置里的提示也补了一句：嫌久可以调小秒数、取消勾选，或者直接点跳过。

保留默认 25 秒的理由：作答时长是最容易被识别的机器特征。但决定权交给用户，不替他扛。

### 28.4 新增测试

`test/save.test.js` 扩到 37 项：

- **只有 `answertype` 时读不到值**（防止把题型当答案）
- 同时存在时能跳过 `answertype` 读到真正的 `answerXXX`
- 多选题集合核对：少了、多了都判不一致

## 三十、v1.1.0 变更（作业也自动做，整条链闭环）

### 30.1 为什么能做到

`Main.init()` 里有一条：

```js
if (!isTop && this.canAccessTop()) { window.__llmqChild = true; return; }
```

**子框架直接退出，一行逻辑都不跑**。也就是说，作业页 iframe 里的脚本是空转的——答题一直是顶层的 `Runner` 通过 `Main.resolveQuizDoc()` 定位到那个 iframe 的 document，然后直接操作它的 DOM 完成的。

推论：`CoursePilot` 和 `Runner` **活在同一个 window 里**，通信不需要跨帧协议，直接 `await Runner.start()` 就行。

这比原脚本那套 `_w.top.unrivalWorkDone` 全局标志干净得多。

### 30.2 实现

主循环里视频之后加一段：

```js
const hw = this.detectHomework();
if (hw) {
  if (this.ranHomework()[hw.key]) { /* 已做过，跳过 */ }
  else { await this.runHomework(); this.markHomework(hw.key); }
}
```

`runHomework()` 做三件事：检查 API Key → `Main.resolveQuizDoc(true)` 重新定位装题文档 → `await Runner.start()`。

### 30.3 去重：同一份作业不能反复做

`detectHomework()` 返回的 key 是「首个题目 id + 题目数量」。同一份卷子翻页重载都不变，换一份就变。

**不管做没做成功都记下来**（D-54）。否则模型没配好、答案全跳过时，会对着同一份卷子无限重试同一批请求——既烧 token 又卡死流程。

存 `sessionStorage`，关标签即清。

### 30.4 一个容易踩的坑

第一版判断写的是 `typeof Main === 'undefined'` 就跳过。但 `Main` 在 90-main.js 里**只有顶层会初始化**，单元测试里根本没加载它 → 永远走"模块没加载"分支，测不到真正的逻辑。

改成只依赖 `Runner` 和 `Config`（这两个是真的答题必需），`Main` 降级成可选的辅助。

### 30.5 新增测试

`test/course.test.js` 扩到 31 项：

- 作业标识能取到首个题目 id

- 不同卷子的 key 不同

## 三十一、v1.1.1 变更（作业没做完就跳走）

### 31.1 根因：失败分支少了一个 break

```js
const ok = await this.runHomework();
this.markHomework(hw.key);
if (this.stopFlag) break;
await sleep(4000);
if (ok) continue;      // ← 失败时不 continue
// 于是直接往下走到 nextSection()，把没做完的作业绕过去
```

`runHomework()` 返回 false（没配 Key、解析失败、覆盖率不足）时，代码没有停，继续执行到"点下一节"。**整节作业被跳过，而且被标记成"已做过"**，之后不会再试。

### 31.2 只看 `start()` 有没有返回是不行的

`Runner.start()` 有六七条提前返回的路径：没解析到题、有未支持题型、覆盖率不足、保存失败、被"未完成"弹窗拦住……**每一条都正常返回**。父页面无法从"它返回了"推断出"这节做完了"。

原脚本的做法值得借鉴——它不看返回值，看两个信号：

```js
// 1) 所有请求回来了才继续（busyThread 计数）
var workInterval = setInterval(function() {
    if (busyThread != 0) return;
    ...
}, 1000);

// 2) 作业页自己上报"我完成了"，父页面轮询这个标志
if (_w.top.unrivalWorkDone) { ...标记任务完成... }
```

**完成信号由作业页主动发出，而不是父页面猜。**

### 31.3 改法：让 Runner 留下一份结果

给 `Runner` 加 `lastResult`，在 `finish()` 的每个结束分支赋值：

| status | 含义 |
|---|---|
| `done` | 填满 + 已提交 / 已保存 → **只有这个算做完** |
| `filled` | 填了但没落库（只填不存、保存失败） |
| `incomplete` | 没填满（覆盖率不足、有未支持题型、解析不到题） |
| `stopped` | 用户点了停止 |
| `error` | 没配 API Key、运行中断 |

`runHomework()` 只认 `done`，其它一律返回 false；主循环收到 false 就 **break**，并明说「继续往下会把它绕过去」。

拿不到 `lastResult` 时按"没做完"处理——**不乐观放行**。

### 31.4 标记时机也改了

原来"不管成败都标记"（怕反复重试）。现在失败会 break，不存在死循环，所以改成**只在成功时标记**：用户修好配置后重新点刷课，这份作业会重新尝试。

### 31.5 日志

每轮开始打一行状态，作业结束打一行判定依据：

```
第 3 轮：无视频，有作业
这一节是作业，自动开始答题
...
这一节作业结束：incomplete，覆盖率 50.0%，未保存
  原因：覆盖率 50.0% 未达 100%
这一节作业没做完，自动刷课已暂停 —— 继续往下会把它绕过去
```

### 31.6 新增测试

`test/course.test.js` 扩到 36 项，核心是**完成判定**：

- 覆盖率不足 → false
- 填满且已保存 → true
- **只填不存 → false**（答案没落库，跳过去就白做）
- 中途停止 → false
- **拿不到结果 → false**（不乐观放行）

总计 382 项。

## 三十二、全面自查（v1.1.1 追加修复）

### 32.1 判断题的值核对是错的

选项 key 是 A/B，而超星在 `answer` 字段里给判断题存的是 `true/false`：

```js
if (q.type === 'judge') return want.some((k) => got.indexOf(k) >= 0);
// want = ['A']，got = 'true' → 'true'.indexOf('A') === -1 → false
```

**所有判断题都会被判成"点击未生效"**——点上了也报错，然后触发重试，重试又对着已选中的选项再点一下（toggle），答案又被点掉。

修复：判断题只判断字段非空（答了就是答了，选对没选对是模型的活）。

### 32.2 多选题的字段值可能带分隔符

超星可能存 `'ABC'`、`'A,B,C'` 或 `'A B C'`。原实现直接 `split('')`，逗号和空格会混进集合，比对失败。先 `replace(/[^A-Z]/g, '')` 归一化。

### 32.3 isOptionChecked 对判断题同样有这个坑

修复了 verifyChoiceValue 但漏了 isOptionChecked——它也拿选项 key 去字段值里找。判断题的所有选项（A/B）都会被判"未选中"。

好在判断题的 `<li>` 上带 `val-param="true|false"`，和字段值同构，直接比这个：

```js
const vp = opt.clickEl.getAttribute('val-param');
if (vp) return String(vp).toLowerCase() === String(val).toLowerCase();
```

### 32.4 目录遍历的 idx = -1 陷阱

```js
const idx = nodes.findIndex((n) => n === act);
for (let i = idx + 1; i < nodes.length; i++) { ... }   // idx=-1 时从 0 开始！
```

`act` 是 `.posCatalog_active`，`nodes` 是 `.posCatalog_select`——两套选择器，如果它们不是同一组元素，`findIndex` 返回 -1，循环从第 0 个开始，**会点到第一节甚至当前这一节**，然后原地打转。

修复：`idx < 0` 直接放弃目录方案，落后面的老版兜底。宁可不动，不可点错。

### 32.5 点不动「下一节」时的死循环

点了没反应，下一轮还会找到同一个元素，再点——循环上限是 300 轮 × 6 秒 = 30 分钟空转。

修复：连续两次点同一个元素页面没变化 → 判定它点不动，停止并报告。

### 32.6 已播完的视频会被再次选中

`findVideo` 只查 `duration` 就绪，不查 `ended`。视频播完后如果页面没刷新，下一轮循环还会找到它，`play()` 之后立即 `ended`，然后继续下一轮……死循环。

修复：`!v.ended` 加入筛选。

### 32.7 两处状态互斥

- 用户在刷课期间点「开始答题」：Runner 和 CoursePilot 会同时操作页面，两边的选择判断互相干扰。UI 层拦住并提示。
- 点「停止」：如果刷课在跑，停的是整个刷课流程（之前只停 Runner，刷课会继续跑）。

### 32.8 新增测试

- 判断题不因 key 是 A/B 而判失败
- 多选 `A,C` 带分隔符能正确比对
- 判断题 `val-param=true` 判已选、`false` 判未选
- active 不在候选列表时返回 null（宁可不动，不可点错）

## 三十四、v1.2.0 变更（学原脚本的关键一招：读任务清单，不再摸黑找）

### 34.1 用户日志暴露的核心缺陷

```
第 2 轮：无视频，无作业 → 进入下一节
第 3 轮：无视频，无作业 → 进入下一节
```

而目录里清清楚楚标着「1个待完成任务点」。

原因：自动刷课靠**等 DOM 渲染出来再找 video/作业**，任务 iframe 加载慢于重试窗口（7 秒）时，直接被判成"这节没任务"然后跳走。目录里有任务点、脚本却视而不见。

### 34.2 原脚本的解法（这次真的学了）

它在 `knowledge/cards` 页面**读 script 里的任务清单**，不等任何渲染：

```js
param = getStr(scripts[i].innerHTML, 'try{\n    mArg = ', ';\n}catch(e){');
// JSON.parse(param) → attachments: [{type, job, isPassed, property, jobid, jtoken...}]
```

清单是确定性的：这一节有几个视频、几篇文档、有没有作业、做没做完，全写在里面。

### 34.3 实现

`findMarg()` 递归帧树（≤4 层）找含 `mArg = {...}` 的 script；`parseTasks()` 把 attachments 拆成视频/文档/作业三列，`isPassed` 的不进待办但计入 `totalJobs`。

主循环改成清单优先：

| 清单内容 | 动作 |
|---|---|
| 有视频 | 等元素出现（30s）→ 真实 1x 播放 |
| 有文档 | 调超星自己的「阅读完成」接口（用户打开文档时浏览器本来就会发这个请求） |
| 有作业 | 等作业页面出现（10 分钟，用户可手动点开）→ 交给 Runner |
| 全部处理完 | 点「下一节」 |
| 没有清单 | 退回原来的 DOM 摸索逻辑 |

**「任务点全做完」直接下一节**，不白耗 DOM 重试的 7 秒。

### 34.4 解析里的两个坑

```js
const jsonEnd = text.lastIndexOf('}', catchAt);      // ← 错：把 try 块自己的 '}' 卷进来
const jsonEnd = text.lastIndexOf('}', catchAt - 1);  // ← 对
```

`catchAt` 指向 try 块的闭合 `}`，包含它会让 JSON 后面多出 `;\n}`，`JSON.parse` 直接报错。范围必须排除 `catchAt` 那一位。

另外解析前要过滤带 `==UserScript==` 标记的 script——我们自己脚本的注释里也有 "mArg" 字样。

### 34.5 文档任务的边界说明

「阅读完成」接口是用户点开文档时浏览器本来就会发的，代发一份等价于"打开过这篇文档"，**不涉及时长伪造**。视频仍然 1 倍速真实播放，这条边界没动。

### 34.6 新增测试

`test/course.test.js` 扩到 48 项：

- 从 script 解析出 mArg（真实格式，含嵌套 JSON）
- 任务分类：未完成视频/文档/作业各就各位，`isPassed` 的不计入待办但计入 totalJobs
- `mArg = ""` 的空页面、无 mArg 的页面都返回 null
- **带 `==UserScript==` 标记的 script 不解析**（防止解析自己）
- 解析自己的脚本文本含 "mArg" 字样时不误判

解析 JSON 的边界（`catchAt-1`）是通过直接复现提取逻辑发现并验证的。

总计 398 项。

## 三十三、v1.1.2 变更（导出诊断说"没题"，页面上明明有）

### 33.1 用户贴的诊断暴露的盲区

在课程学习页导出，输出说「最终采用: 无」「题目总数: 0」，但日志同一时刻显示「解析成功：cx-pc + 填空，共 60 题」。

矛盾的原因：**题目藏在 iframe 深处**，结构是：

```
顶层 studentstudy（depth 0）
  └─ knowledge/cards（depth 1）
       └─ 作业 iframe（depth 2）
            └─ 部分课程还有一层（depth 3）← collectDocs 到这里就停了
```

`collectDocs` 只递归两层，最后一层摸不到。

### 33.2 修了四件事

| 修复 | 说明 |
|---|---|
| collectDocs 深度 2 → 4 | 顶层、cards、作业、再深一层都能收到 |
| 任务点检测加重试 | 刚进新节时作业 iframe 往往还没加载。原来不检测就点「下一节」=整节跳过。现在没找到时等 3.5 秒 ×2 再放弃 |
| 目录遍历跳过章标题 | `.posCatalog_select.firstLayer` 是章标题，没有 id、没有任务点，点它只是展开目录。原来会被当成候选，可能点到章上 |
| 点掉「继续学习」弹层 | 跳到有未完成任务的节时超星会弹确认，不点掉页面就停在弹层上 |

### 33.3 诊断/导出的兜底

`diagnose` 和「导出页面结构」在定位不到题目时，现在会**主动在所有 iframe（含深层）里找一次**并标注「从 iframe 深处解析到 N 题」——诊断工具自己得先信得过，不然排查问题第一手信息就是错的。

### 33.4 新增测试

目录章节遍历对 `firstLayer` 的过滤：active 后面如果是章标题 + 两个普通节，必须落在第一个普通节上，不能点到章标题。

## 34. v1.4.3 – v1.6.5：调度修完后的收尾（2026-10-30 下午）

### 34.1 「下一节」按钮的真面目（D-56）

用户反复报"没做完就跳/跳不动"，对照 chaolucky/xuexitongScript 项目后确认：cards 页面每节有**步骤**（学习目标→视频→测验），底部的「下一节」按钮在这些步骤之间推进，**不是切节**。跳节顺序改为：目录树（当前高亮的下一节）→ `#prevNextFocusNext`（测验步骤的跳过）→ 底部按钮 → 文字匹配。进新节后找不到播放器时，先点顶部「2视频」页签把步骤切过去。

### 34.2 作业链路只进不停（D-58）

- 提交后**验证页面跳到批阅页**才认账（原脚本的完成信号），验证不过按未提交处理——"调用成功"不等于"提交成功"；
- 覆盖率不足 / 含填空等写不进的题型 → 保存即继续，继续前报告空题号（`reportUnfilled`）；
- 保存失败 → 重试一次，仍失败也继续并标注「未落库」；只有自动保存被关闭才停。

### 34.3 猜题兜底（原脚本 randomDo）

模型没匹配到答案时按题型猜默认值（单选 B / 多选全选 / 判断错）。来源是实测：60 题卷子因 1 题点击失效卡在 98.3%，整卷不交的损失远大于差一题。

### 34.4 字形视觉识别（D-60）

对照表没收录的乱码字形，用 FontFace 渲染成 96px 图发给视觉模型认字，结果按字形哈希写入本地扩展表（`llmq:glyphExtra`）永久生效。测试时抓出「是【党】。」被解析成「是」的 bug——提取答案要先剥标点、去开头"是/答案"再取汉字。

### 34.5 两个 UI 决策

- 主按钮合一：课程页显示「自动刷课」、答题页显示「开始答题」，同一位置动态切换（原先两个按钮靠页面类型显隐，判定一错就打架）；
- 作业窗口收起成横条并逐题播报 n/N（D-59）——完全隐形会让用户以为卡死。

### 34.6 新增测试

- 保存后的完成判定（decideAfterSave 四种组合）
- 字形视觉识别全流程（mock 视觉模型：识别成功/杂质提取/跳过已识别/网络失败/未配模型/停止指令）38 → 61 项
